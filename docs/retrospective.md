# Claude와 둘이서 만든 우리 결혼식 청첩장 — 개발 회고

> 방문자 1,847명 · 방명록 사진 412장 · 인프라 비용 0원

## 들어가며

2026년 10월 24일, 결혼했다. 예식이 끝나고 한 달쯤 지나 이것저것 정리하다가 청첩장 관리자 페이지를 열었는데, 방명록에 168개의 글과 412장의 사진이 쌓여 있었다. 하객들이 각자의 폰으로 찍은 우리 결혼식이, 원본 화질 그대로. 별거 아닌데 이상하게 뭉클해서, 잊기 전에 이 청첩장을 어떻게 만들었는지 적어둔다.

결론부터 말하면 — 디자인 프로토타입부터 배포, 예식 당일 운영까지 Claude Code와 페어로 만들었고, 커밋 43개, 서버 비용은 0원이었다.

## 왜 직접 만들었나

시중 모바일 청첩장도 충분히 예쁘다. 그런데 개발자로서 양보하기 싫은 게 몇 개 있었다.

- 하객이 올려주는 사진을 **압축 없이 원본 그대로** 받고 싶었다
- 방명록 사진 업로드 장수 제한이 싫었다
- 지인용/친인척용 문구를 링크 하나로 분기하고 싶었다 (`?to=family`)
- 그리고… 개발자 친구들한테만 보낼 **터미널 버전 청첩장**을 만들고 싶었다

## 스택

- **Next.js 15 (App Router) + Vercel Hobby** — 이미지 최적화, API Routes, cron까지 한 곳에서
- **Supabase Postgres** — 방명록·RSVP. 전 테이블 RLS deny-all로 잠그고 서버(service role)로만 접근
- **Cloudflare R2** — 사진 원본 저장. presigned PUT으로 브라우저에서 직접 업로드
- **Kakao SDK** — 공유 카드, 오시는 길 지도

## "이미지 압축 안 하고 싶어" 한마디가 아키텍처를 정했다

설계 초기에 Claude는 "클라이언트에서 리사이즈해서 올리면 Supabase 무료 1GB로 충분하다"는 합리적인 안을 냈다. 나는 한 줄로 답했다. *"이미지 압축 안 하고 싶어."*

이 한마디로 설계가 뒤집혔다. 폰 사진 원본은 장당 3~8MB라 1GB로는 어림도 없다. 스토리지는 R2(무료 10GB, egress 0원)로 바뀌었고, 업로드는 Vercel 함수의 4.5MB body 제한을 우회해 presigned URL로 브라우저→R2 직행하는 구조가 됐다. 대신 화면에 뿌릴 때는 next/image가 만든 썸네일을 Vercel CDN에 캐시하고, 원본은 라이트박스에서 탭했을 때만 로드한다. 원칙은 하나다 — **저장은 무손실, 전송만 최적화.**

E2E 테스트에서 Claude는 11MB짜리 사진을 업로드한 뒤 R2에서 다시 내려받아 md5를 비교했다. 바이트가 정확히 같았다. 예식이 끝난 지금, R2에는 3.1GB의 원본이 쌓여 있다.

## 삽질 모음

**① EXIF 지옥.** 스튜디오 사진 47장을 갤러리에 넣었더니 40장이 "픽셀은 가로로 저장 + 90도 돌려 보라는 메타데이터"가 붙은 EXIF 회전 사진이었다. Next.js는 픽셀은 돌려서 내보내는데 코드에 주는 크기 정보는 안 돌려줘서 프레임이 죄다 어긋난다. jpegtran으로 DCT 블록만 재배열하는 **무손실 회전**을 일괄 적용해서 해결했다 — 재인코딩 0회, 화질 손실 0.

**② 대문자 `.JPG`의 배신.** 타입 선언이 안 맞는 건 예상했는데, 진짜 함정은 따로 있었다. 대문자 확장자로 static import하면 **blur placeholder가 생성되지 않아 런타임 에러**가 난다. 결국 45장 소문자 일괄 리네임.

**③ 빈 문자열 env.** `process.env.X ?? "fallback"`은 빈 문자열을 못 거른다. Vercel에 빈 값으로 등록된 환경변수 하나가 `TypeError: Invalid URL, input: ''`로 빌드를 터뜨렸다. `||`로 바꾸고, Vercel이 자동 주입하는 `VERCEL_PROJECT_PRODUCTION_URL` 폴백을 깔았다.

**④ dev 서버 떠 있는데 `next build`.** `.next`가 오염되면서 CSS가 404 나고, 청첩장 첫 화면 위로 다음 섹션이 겹쳐 보이는 대참사. 부끄럽게도 두 번 겪었는데, 두 번째는 Claude가 저질러놓고 스스로 원인을 찾아내 사과했다 ㅋㅋ

**⑤ 19.3Mbps 릴스 영상.** 커버 영상 원본이 67MB였다. 로컬에 ffmpeg이 없자 Claude는 mp4 박스 구조를 Node로 직접 파싱해서 moov atom 위치(스트리밍 시작 가능 여부)와 비트레이트를 확인하더니, CRF 22로 14.4MB까지 줄였다. 예식장에서 하객들이 우르르 접속해도 영상이 안 끊긴 건 이 덕분이라고 생각한다.

## 개발자용 청첩장, `/dev`

제일 재밌었던 부분. 같은 정보를 Dracula 테마 터미널로 보여주는 페이지를 따로 팠다. 접속하면 `wedding --info`가 자동으로 타이핑되고, RSVP는 inquirer 스타일 프롬프트(`? 어느 쪽 하객이신가요 › ● 신랑측`)로 진행되며, 계좌번호 옆에는 `| pbcopy` 버튼이 붙어 있다. `sudo marry`를 치면 *"Permission granted. 두 사람의 결혼이 승인되었습니다. 💍"* 가 나온다.

`claude "축사 부탁해"` 명령도 있는데, 진짜 API 호출은 아니고 정규식 매칭 + 준비된 답변이다. 공개 페이지에 LLM을 그대로 물리는 건 비용과 프롬프트 인젝션 양쪽으로 무서운 일이라, "✳ Thinking…" 연출만 진짜처럼 했다.

이 페이지에 **213명**이 다녀갔다. 하객 중 개발자 비율을 생각하면, 링크가 생각보다 많이 돈 것 같다.

## 예식 당일 숫자

- 순 방문자 **1,847명**
- 당일 오전 11시대 최고 동시 접속 **743명**
- 방명록 **168건**, 사진 **412장 (3.1GB)**
- 친인척 링크(`?to=family`) 방문 **141명**
- 이미지 변환 **4,102 / 5,000회** — 무료 한도의 82%

743명이 동시에 붙었을 때 서버는 아무 일도 없었다. 정적 자산과 방명록 썸네일은 CDN 캐시가 다 받아냈고, R2로 직행하는 트래픽은 라이트박스 원본뿐이었다. 설계 단계에서 "예식 당일 예식장 기지국 혼잡"까지 걱정하며 영상을 CDN 쪽으로 옮겨놨는데, 그 시나리오가 실제로 왔고, 그래서 아무 일도 없었다.

이미지 변환 수치도 흥미로웠다. 설계 때 "방명록 썸네일을 고정 폭 단일 변환으로 묶으면 무료 한도 안"이라고 계산했는데, 실측 4,102회로 거의 들어맞았다.

## AI와 페어로 일한다는 것

- **좋았던 것은 검증 루프.** Claude는 "됐습니다"라고 말로 때우지 않았다. puppeteer로 6개 뷰포트의 오버플로우를 픽셀 단위로 실측하고, 스크린샷을 찍어 제 눈으로 확인하고, 프로덕션에 직접 E2E를 돌렸다. 배포가 실패했을 때는 Vercel 로그를 까서 빈 환경변수를 찾아냈다.
- **의외였던 건, 실수도 사람같이 한다는 것.** 같은 빌드 사고를 두 번 냈고, `tail -2`로 출력을 잘라 보고 "40장 회전 성공"이라 오판했다가 스스로 번복하기도 했다.
- **결정은 끝까지 내 몫이었다.** 압축 거부, R2 선택, 도메인 이름, 캘린더 디자인 레퍼런스 — AI는 선택지와 트레이드오프를 근거와 함께 정리해줬고, 고르는 건 내가 했다. 지금 시점의 AI 협업은 이 분업이 맞다고 느꼈다.
